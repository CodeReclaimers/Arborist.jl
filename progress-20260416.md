## Fix flaky Windows CI: LLM latency measurement used coarse `time()`

### Summary

Investigated recent failing CI on the 2026-04-15 "Ablation study" commit
(run 24434156056). All failures were Windows-only across the three
Windows matrix entries (Julia 1.10 / 1.11 / nightly); macOS and Linux
jobs all passed. A single test assertion was failing:

```
LLMCallStats accumulation on success: Test Failed at
  test/integration/test_llm_operator.jl:549
  Expression: s.total_latency > 0.0
   Evaluated: 0.0 > 0.0
```

### Root cause

`src/llm_operator.jl` measured HTTP wall-clock latency with
`dt = time() - t0`. Julia's `time()` returns `gettimeofday`-equivalent
seconds and, on Windows, has coarse resolution — historically ~15 ms
and still far below the nanosecond range on modern systems. The test
installs a mock HTTP hook that returns a canned response effectively
instantly, so on Windows `dt` rounds to exactly `0.0` and the strict
`> 0.0` check fails. Linux/macOS observed enough sub-millisecond jitter
between the two `time()` reads that the assertion coincidentally passed.

### Files modified

- **`src/llm_operator.jl`** (lines 225, 229, 237) — replaced `time()`
  with `time_ns()` for the three latency-measurement points (start, catch
  branch, success branch). `time_ns()` returns a `UInt64` nanosecond
  counter with sub-microsecond resolution on all platforms including
  Windows. Divide the delta by `1e9` to preserve the `total_latency`
  field's existing "seconds" units, so no downstream consumer breaks.
  Added a one-line comment at the `t0 =` site explaining the Windows
  motivation.

- **`progress-20260416.md`** — this entry.

### Decisions and alternatives considered

- **Chose source-side fix (`time_ns()`) over weakening the test.**
  The adjacent test at `test_llm_operator.jl:578` already uses
  `total_latency >= 0.0` with the comment "mock is instant; real calls
  take seconds". Changing line 549 to match would have been a one-char
  edit and the minimal diff. Rejected because `>= 0.0` is satisfied
  even if `total_latency` is never written — it no longer verifies the
  accumulation behavior the test was written to check. The `time_ns()`
  change improves latency-measurement accuracy across the whole
  operator while keeping the test assertion meaningful.

- **Did not modify `:578`.** The parse-failure test's `>= 0.0` with the
  explanatory comment remains a reasonable hedge for live-API mode
  where the mock is swapped out and the post-parse-failure latency can
  still legitimately be tiny. No behavior change needed there.

### Verification

- Full test suite on Linux (Julia 1.11.5): 3198 passed, 1 broken,
  1m10.8s. The "broken" is the expected `@test_skip` for
  `ANTHROPIC_API_KEY not set` in `test/integration/test_llm_operator.jl`.
- `grep '\btime()'` on `src/llm_operator.jl` confirms no remaining raw
  `time()` calls (one comment reference intentionally kept).
- Could not reproduce the failure locally (no Windows runner) — the
  CI re-run after push will be the final verification.

  green.
- If any other latency-style measurement exists in the codebase that
  uses `time()`, consider migrating it to `time_ns()` for the same
  reason. Did not do a sweep in this session; scope was the reported
  failure only.
