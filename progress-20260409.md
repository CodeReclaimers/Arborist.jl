# 2026-04-09 — Sanitizer whitelist bug: diagnosis and fix

## Summary

The post-fix LLM bin-packing rerun (launched 2026-04-08) completed
overnight. Both G1B (300 gen) and G2C (5 seeds × 100 gen) finished
without errors, but analysis of the logs revealed a second latent bug:
the ASTSanitizer was rejecting 98.9% of LLM mutations.

## Diagnosis

The `llm_ok` counter in the `TrackedMutation` wrapper
(`examples/bin_packing.jl:358`) is a wall-time heuristic (`dt > 0.5s`),
not an actual mutation success count. It measures "the HTTP call reached
the LLM" — not "the LLM output survived through the full pipeline."
The reported "100% LLM success" was misleading.

Actual counts from the G1B log (300 gens, seed 42):
- LLM HTTP calls: 3653
- Sanitizer rejections: 3612 (98.9%)
- Deserialize returned nothing: 41 (1.1%)
- Mutations that actually used LLM output: ~0

**Root cause:** `src/llm_operator.jl:197` constructed `ASTSanitizer()`
with `DEFAULT_SAFE_CALLS` — a whitelist of math operators, type
conversions, and Julia builtins. Domain-specific functions like
`bp_n_bins`, `bp_bin_remaining`, `bp_place_in_bin` are NOT in that
default set.

The deserializer's `_is_valid_call` (`src/genome/expr_genome.jl:316`)
correctly validates function calls against the GenState's function set
(which includes `bp_*`). But the sanitizer then re-checks against its
own, narrower whitelist and rejects the same calls.

**Why this was masked pre-parser-fix:** The old parser stripped all
control flow and kept only assignments. Assignments use operators
(`+`, `-`, `*`) which are in `DEFAULT_SAFE_CALLS`. The `bp_*` calls
lived inside `while`/`if` blocks that the parser was discarding before
the sanitizer ever saw them. The sanitizer has always had this
limitation — it was just never exercised by any LLM output that
survived parsing.

**Why the `llm_ok` metric didn't catch it:** `TrackedMutation` uses a
0.5-second threshold to distinguish "LLM inference happened" from
"instant fallback to SubtreeMutation." Since the sanitizer runs *after*
the HTTP call, a rejected-then-fallen-back mutation still takes >0.5s
(the LLM inference time) and gets counted as "ok." The metric is
structurally unable to detect sanitizer rejections.

## Fix

Added `_build_sanitizer(state::GenState)` in `src/llm_operator.jl`
that constructs an `ASTSanitizer` whose whitelist is
`union(DEFAULT_SAFE_CALLS, {fd.name for fd in state.funcs.funcs})`.
Changed the sanitizer call at line 197 from `ASTSanitizer()` to
`_build_sanitizer(g.state)`.

This way, any problem-specific primitives registered in the function
set are automatically included in the sanitizer's whitelist. The
deserializer and sanitizer now agree on what function calls are
permitted.

## Files modified

- `src/llm_operator.jl` — added `_build_sanitizer`, changed sanitizer
  construction at the call site

## Synthesis: what the LLM fix actually changed

### The LLM helps on some seeds, hurts on others

Seeds 42 and 1337 improved dramatically (-0.012 each). Seeds 123, 456,
789 were neutral to slightly worse. Mean test fitness is effectively
unchanged (1.0664 vs 1.0700, within one standard deviation). The fix
did not reliably lift performance — it increased variance by enabling
more aggressive mutations that either pay off or don't, depending on
the evolutionary trajectory the seed produces.

### Best-case improved, worst-case unchanged

The best single result across all runs is now seed 1337 at test 1.0531
(4.5% better than Best Fit). Pre-fix best was seed 123 at 1.0616
(2.4% better than BF). The ceiling rose significantly on the seeds
where the LLM connected.

### No novel control flow from the LLM

All evolved best programs across all three runs have the same
structural template: a `while` loop scanning bins 1..bp_n_bins(), an
outer `if` checking capacity, a nested `if` tracking the best-so-far
bin, and a final `bp_place_in_bin` call. This is the textbook Best Fit
heuristic.

The LLM's contribution is **tuning the scoring expression** inside the
comparison (e.g., `__temp_6 <= __temp_5` vs
`__temp_6 * __temp_4 < __temp_5 - __temp_6`). Pre-fix, this tuning
operated on assignment-only fragments (constants and arithmetic within
`__temp_5 = ...` statements). Post-fix, it operates on the full
function body, but the LLM is not introducing `for` loops, `break`,
`continue`, or structurally different control flow.

The parser fix was necessary for **correctness** (the pre-fix runs
were silently discarding valid LLM output) and the sanitizer fix was
necessary for the parser fix to actually matter. But neither unlocked
a qualitatively different class of evolved programs on this benchmark.

### The `llm_ok` metric is misleading

`TrackedMutation` counts wall-time > 0.5s as "LLM success." This
conflates "the HTTP call completed" with "the LLM output survived the
full pipeline (deserialize + sanitize) and became the genome." In run
2, 3612 of 3653 "successful" LLM calls were actually sanitizer
rejections that fell back to SubtreeMutation. The metric should be
redesigned to track actual pipeline-survived mutations. Not fixing
this now — would require changing the tracking interface mid-experiment
series.

## Decisions

- **Not fixing `llm_ok` metric now.** The timing heuristic is
  fundamentally limited but changing the `TrackedMutation` interface
  mid-experiment would invalidate comparisons. Flagged for future work:
  the metric should count actual pipeline-survived mutations, not
  wall-time thresholds.
- **Not rerunning G1A.** The classical control does not go through the
  LLM operator or sanitizer. Run 2's G1A results (train 1.0693, test
  1.0637) are the valid matched baseline.
- **Kept run 2 results in archive.** They're the empirical proof of the
  sanitizer bug's impact (99% fallback rate → effectively classical
  performance). Useful evidence if we ever question whether the
  sanitizer is load-bearing.
- **Committing run 3 result files.** These are the first valid LLM
  bin-packing results — both the parser and sanitizer are now
  functioning correctly. They replace the pre-fix results in-tree.

## Prompt enrichment for LLM mutation operator

### Problem

The LLM mutation operator sent only a system prompt and the serialized
genome — no fitness, no population state, no generation progress. The
LLM operated as a blind, stateless perturbation function. FunSearch and
AlphaEvolve both provide the LLM with scored programs to guide search.

### Implementation (`aba98de`)

Created a configurable prompt enrichment mechanism:

**New file `src/prompt_context.jl`:**
- `MutationContext` — mutable struct with generation, fitnesses,
  serialized elites, and per-call parent fitness/rank. Updated by the
  solve loop each generation.
- `AbstractPromptSection` — base type for composable prompt blocks.
- `FitnessSection` — parent fitness/rank, population best/mean.
- `ElitesSection(k)` — top-K programs with fitnesses (FunSearch core).
- `GenerationSection` — generation number + phase label.
- `render_enrichment` — concatenates non-empty section renders.
- `_update_llm_contexts!` — finds LLM operators in mutation_ops
  (unwrapping wrappers via hasproperty), serializes top-K elites,
  sets population-level context. Called once per generation.
- `_set_parent_context!` — sets parent_fitness and parent_rank.
  Called inside breeding loop after tournament selection.

**Modified `src/llm_operator.jl`:**
- `LLMMutationOperator` changed from `struct` to `mutable struct`.
- Added `sections::Vector{AbstractPromptSection}` (default: empty)
  and `context::Union{MutationContext, Nothing}` (default: nothing).
- `_build_request_body` injects enrichment before genome source in
  the user message, separated by "--- Program to mutate ---".

**Solve loop integration (5 paths):**
- `_run_evolution!` in `src/solve.jl` — after speciation, before
  breeding.
- `_breed_next_generation!` — after tournament selection, before
  mutate.
- Sequential island model in `src/solve.jl` — per-island, per-gen.
- Distributed island in `src/distributed_island.jl` — per-worker.
- NSGA-II in `src/nsga2.jl` — uses first objective as scalar proxy.
- `examples/bin_packing.jl` custom solve loop — both hooks added.

### Ablation experiment infrastructure

Added `run_ablation_enrichment()` to `examples/bin_packing.jl` with
4 variants × 5 seeds:

| Variant | Sections |
|---|---|
| baseline | [] (no enrichment) |
| fitness_only | [FitnessSection()] |
| elites_3 | [ElitesSection(3)] |
| full | [FitnessSection(), ElitesSection(3), GenerationSection()] |

Launcher: `examples/run_ablation_enrichment.sh`. Runs variants
sequentially (GPU contention). `--variant=<name>` for single variant.
Expected wall: ~25 min per variant, ~2 hr total.
