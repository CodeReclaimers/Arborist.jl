## Seed Template Ablation for Sorting Example

### Summary

Added `max_seed_type` parameter to control which seed templates are included in the initial population (0=random only, 1=single-pass only, 2=types 1-2, 3=types 1-3, 4=all including selection sort). Ran ablation experiments to determine whether evolution can discover nested loop structure from a single-pass seed or from scratch.

### Files Modified

- `examples/sorting.jl` — added `max_seed_type` field to `CurriculumSortingEvaluator`, threaded through `run_sorting` kwargs and CLI arg parser
- `arborist_paper_observations.md` — updated section 5.6 with sorting experiment results and comparison penalty findings

### Ablation Results (300 pop × 500 gen, no comparison penalty)

| Config | Final curriculum | Best | Len-3 % | Len-8 % |
|--------|-----------------|------|---------|---------|
| All seeds (types 1-4) | 20 | 0.028 | 100% | 100% |
| Type 1 only, seed=42 | 3 (stuck) | 0.107 | 66.8% | 0.3% |
| Type 1 only, seed=123 | 4 (advanced gen 300) | 0.113 | 84.1% | 0.8% |
| Random only, seed=42 | 3 (stuck) | 0.171 | 31.9% | 0.0% |

### Key Finding

**Evolution cannot discover nested loop structure from a single-pass seed within 500 generations at pop=300.** Both type-1 runs converged to the same structure: a `while true` loop running a single adjacent-comparison pass until the loop limit (5760 iterations). The loop limit acts as a poor substitute for an outer loop — it repeats the pass enough times to partially sort by luck, but scores only 67-84% on length 3.

The seed=123 run managed to advance to curriculum length 4 at generation 300, but only because a mutation added a `sort_swap!(sort_get(78), 72)` call before the loop that happens to pre-shuffle elements favorably. This is a stochastic improvement, not a structural one.

**Why the nested loop is hard to discover:** The mutation operators (SubtreeMutation, PointMutation, HoistMutation, ExpansionMutation) can modify existing loops, add statements inside them, or replace subtrees. But they cannot "wrap" an existing expression in a new loop — that would require simultaneously creating an outer loop with correct bounds AND relocating the inner loop inside it, which is an extremely unlikely compound mutation.

**Implication for the paper:** The seeded templates (especially types 2 and 4 — bubble sort and selection sort skeletons) provide essential architectural scaffolding. Evolution can refine and simplify these structures but cannot discover them de novo at this scale. This matches the bin packing finding: seed templates matter as much as the evolutionary algorithm. For sorting, the nested-loop architecture is a prerequisite that must be provided, not discovered.

### Design Decision: Why this is documented honestly

The prompt's original expectation was that evolution would "independently discover something resembling bubble sort, insertion sort, or selection sort." The ablation shows this does not happen at 300×500 scale without nested-loop seeds. This is reported as a finding rather than hidden — it tells us something real about the difficulty landscape of control-flow synthesis and the role of seeding in GP.

## Distributed Island Model (Phase 1 + Phase 2)

### Summary

Implemented distributed island model where each island runs in its own Julia worker process via `Distributed.jl`. This eliminates the three `@eval` problems in the current single-process island model: serialized compilation (global lock), `invokelatest` overhead (shared world age), and thread-local state workarounds for side-effectful evaluators. Each worker process has its own compilation lock, world age counter, and module-level state.

### Motivation

The current `IslandModel` runs all islands sequentially in one process. For `ExprGenome`-based problems, every `@eval` shares the same global compilation lock, so islands cannot compile evolved programs in parallel. By running each island in a separate OS process, all three problems disappear without any user-facing complexity.

### Files Created

- `src/topology.jl` — `RingTopology`, `CompleteTopology`, `RandomTopology` structs with `migration_targets` dispatch. Ring is the default (backward compatible). Literature suggests ring pairs well with synchronous mode; random/complete pair better with async.
- `src/migration.jl` — `MigrantGenome` struct (serializable genome payload + fitness + type tag) with `to_migrant`/`from_migrant` for all three genome types (ExprGenome, AntGenome, GraphGenome). Only `Vector{Expr}` bodies go across the wire; GenState and compiled functions are reconstructed locally.
- `src/distributed_island.jl` — Worker-local island state (`IslandState{G}` mutable struct), worker-local storage dict (`_local_islands`), and all worker-side functions: `_init_island_local`, `_evolve_one_gen_local!`, `_get_migrants_local`, `_inject_migrants_local!`, `_get_final_state_local`, `_cleanup_island_local`. Also contains `_acquire_workers`, `setup_workers`, `_distributed_sync_solve`, and `_distributed_migrate!`.
- `test/unit/test_topology.jl` — topology target computation tests (ring wrap-around, complete all-to-all, random clamping)
- `test/unit/test_migrant_genome.jl` — MigrantGenome round-trip tests for ExprGenome and AntGenome, deep-copy isolation test
- `test/integration/test_distributed_islands.jl` — backward compatibility test, insufficient-workers error test, sync distributed solve with 2 real worker processes

### Files Modified

- `src/abstractions.jl` — added `AbstractTopology` abstract type
- `src/algorithm.jl` — `IslandModel` struct gains `topology::AbstractTopology`, `distributed::Bool`, `async::Bool` fields with backward-compatible defaults (`RingTopology()`, `false`, `false`). Constructor validates `async && !distributed`.
- `src/solve.jl` — `_migrate!` refactored to use topology dispatch instead of hardcoded ring. `solve(::GPProblem, ::IslandModel)` gains `auto_addprocs`/`auto_rmprocs` kwargs and dispatches to `_distributed_sync_solve` when `distributed=true`.
- `src/Arborist.jl` — added `using Distributed`, new includes (topology.jl, migration.jl, distributed_island.jl), new exports (topology types, MigrantGenome, to_migrant, from_migrant, setup_workers)
- `Project.toml` — added `Distributed` to `[deps]` (stdlib, required for package precompilation)
- `Manifest.toml` — resolved with Distributed
- `test/runtests.jl` — added includes for new test files

### Design Decisions

**Distributed.jl always imported** — it's stdlib and the overhead is minimal. Required adding it to Project.toml for package precompilation to work.

**Worker lifecycle user-managed by default** — `auto_addprocs=false` and `auto_rmprocs=false` on `solve`. Clear error message when workers are insufficient. When `auto_addprocs=true`, only the needed workers are added; when `auto_rmprocs=true`, only workers added by this solve call are removed.

**`@everywhere` cannot be used inside functions in precompiled packages** — discovered during implementation. The `@everywhere` macro is a top-level expression and causes `syntax: "toplevel" expression not at top level` when used inside a function that's `include`d during precompilation. Replaced with `remotecall_fetch` + `Core.eval(Main, :(using Arborist))` equivalents.

**Worker-local state via module-level Dict** — each worker stores its `IslandState` in `_local_islands[island_id]`. Worker-side functions take the island ID and look up state locally. This avoids serializing the entire island state on every `remotecall` — only status tuples and migrant genomes cross the wire.

**Evaluator availability check** — before starting distributed evolution, the coordinator verifies that custom evaluator types (those not defined in the Arborist module) exist on all workers via `remotecall_fetch(isdefined, w, Main, type_sym)`. Gives a clear error message with instructions to use `@everywhere include(...)`.

## Async Distributed Islands (Phase 3) + Sorting Example (Phase 4)

### Summary

Implemented asynchronous distributed island model and a three-way comparison example (sequential vs sync distributed vs async distributed). The async mode provides genuine wall-clock speedup by eliminating coordination overhead between islands.

### Files Created

- `examples/sorting_distributed.jl` — standalone script comparing all three modes on a sorting problem (2 islands, 50 pop × 50 gen, length-6 arrays)

### Files Modified

- `src/distributed_island.jl` — added `AsyncStatusMessage` struct, `_run_island_async` worker-side function, `_distributed_async_solve` coordinator function
- `src/solve.jl` — replaced async error message with dispatch to `_distributed_async_solve`
- `test/integration/test_distributed_islands.jl` — replaced "not yet implemented" test with real async integration test (addprocs(2), 2 islands, 15 gen)

### Design Decisions

**Non-blocking channel operations everywhere** — `_run_island_async` uses `try/catch` on `InvalidStateException` for all `put!`/`take!` calls. A fast island never blocks on a slow island's full inbox. Dropped migrants are acceptable since the same genetic material reappears in future migration events.

**Bounded channel capacity** — Migration inboxes hold at most 4 batches. Status channel holds `n_islands × 10` messages. This bounds memory without requiring backpressure logic.

**`AsyncStatusMessage` concrete struct** — used instead of NamedTuple to ensure reliable cross-process serialization. NamedTuples with specific field names can have serialization issues across processes with different world ages.

**`sleep(0.1)` in coordinator polling loop** — prevents busy-wait. 100ms polling frequency is adequate for monitoring — we don't need sub-generation latency for progress display.

**Fitness history is sparse for async** — one entry per status message received, not one per generation. This is inherent to async mode where there's no well-defined global generation counter. Documented in the function docstring.

### Benchmark Results

| Mode | Wall Time | Speedup | Best Fitness |
|------|-----------|---------|--------------|
| Sequential (in-process) | 5.39s | 1.00x | 0.4715 |
| Sync distributed | 5.86s | 0.92x | 0.4715 |
| Async distributed | 3.66s | 1.47x | 0.4715 |

Sync is slower than sequential at this scale because `remotecall`/`fetch` overhead (~200ms total for 50 gen × 2 islands) exceeds the compilation parallelism benefit on fast evaluations. Async wins because islands run truly in parallel without waiting for each other.

### Test Results

1226 tests pass (1225 pass + 1 pre-existing broken). All four phases of the distributed island plan are now complete.

## Replace HTTP.jl with Downloads.jl (stdlib)

### Summary

Replaced the HTTP.jl weakdep/extension with Downloads.jl (stdlib, available since Julia 1.6). Since Downloads is always available, the LLM operator no longer needs to be a package extension — it moved into core. This eliminated HTTP.jl and 13 transitive dependencies (CodecZlib, OpenSSL, MbedTLS, URIs, ConcurrentUtilities, etc.).

### Motivation

HTTP.jl was the only external weakdep not related to DynamicExpressions. The actual API surface used was a single `HTTP.post()` call. Downloads.jl (stdlib, built on libcurl) covers this use case with `Downloads.request()`, removing the need for users to `Pkg.add("HTTP")` before running LLM experiments.

### Files Created

- `src/llm_operator.jl` — LLM mutation operator, moved from `ext/LLMOperatorExt.jl` into core. Uses `Downloads.request()` with explicit HTTP status code checking (>= 400 throws with status and body).

### Files Deleted

- `ext/LLMOperatorExt.jl` — replaced by `src/llm_operator.jl`

### Files Modified

- `src/Arborist.jl` — added `include("llm_operator.jl")`, added `LLMMutationOperator` to exports
- `Project.toml` — removed HTTP from `[deps]`, `[weakdeps]`, `[extensions]`, `[compat]`, `[extras]`, `[targets]`. Added `Downloads` to `[deps]`. Removed `LLMOperatorExt = "HTTP"` from `[extensions]`.
- `Manifest.toml` — resolved; HTTP and 13 transitive deps removed, Downloads (stdlib) added
- `test/integration/test_llm_operator.jl` — removed `using HTTP` and `Base.get_extension` call. Tests now use `LLMMutationOperator` directly (exported from core). Mock install/restore calls no longer take an extension argument.
- `test/mocks/mock_http.jl` — simplified: `MockHTTPResponse` struct removed (mock now returns plain `String` response bodies). `install_mock_http!()` and `restore_http!()` reference `Arborist._http_post` directly instead of receiving an extension module.
- `examples/bin_packing.jl` — removed conditional `@eval using HTTP` block and `@isdefined(HTTP)` check. Replaced two `HTTP.post()` calls (Ollama health checks) with `Downloads.request()`.

### Key Design Decisions

**Moved LLM operator from extension to core.** The extension pattern (`[weakdeps]`/`[extensions]`) existed because HTTP.jl was external — the operator should only load when the user has HTTP.jl installed. Downloads.jl is a stdlib that's always present, so the extension would always load, making it effectively core code with unnecessary indirection. Moving it into `src/` eliminates the extension machinery.

**Explicit HTTP status checking.** HTTP.jl throws `HTTP.StatusError` on 4xx/5xx responses by default. Downloads.jl returns the response regardless of status code. The new `_default_http_post` explicitly checks `resp.status >= 400` and throws with the status code and response body. This preserves the fail-loud behavior that the `try/catch` fallback pattern relies on.

**Hook returns String instead of response object.** The old `_http_post` hook returned an `HTTP.Response` (with `.body::Vector{UInt8}`), requiring a `_get_response_body` helper to extract the string. The new hook returns `String` directly, eliminating the helper and simplifying the mock infrastructure.

**Downloads added to [deps], not used implicitly.** Even though Downloads is a stdlib, it must be declared in `[deps]` for `using Downloads` to work in a precompiled package module.

### Alternatives Considered

**Keep HTTP.jl as extension, just use it less** — rejected because the entire point was to eliminate the external dependency. The extension pattern adds complexity (separate module, `Base.get_extension` in tests, conditional loading in examples) that is unnecessary when the underlying HTTP library is a stdlib.

**Use Downloads without [deps] declaration** — doesn't work in precompiled packages; Julia requires explicit declaration.

### Test Results

All 1225 tests pass (+ 1 pre-existing broken). No test behavior changes — the mock infrastructure exercises the same code paths, just with a simpler interface.

## Remaining Tier 4 Review Fixes

### 4.2 — Convergence threshold parameterized

Added `convergence_threshold::Float64` field to `GeneticProgramming` (default `Inf`). The old hardcoded `fitnesses[1] < 1.0` check was meaningless for many problems (e.g., bin packing fitness is always > 1.0). Replaced all six occurrences across `src/solve.jl`, `src/distributed_island.jl`, `src/genome/ant_genome.jl`, and `src/genome/graph_genome.jl` with `< algorithm.convergence_threshold`. Default `Inf` means `converged` is never set unless the user specifies a meaningful threshold.

### 4.5 — FunctionDetails isequal uses field comparison

Changed `Base.isequal(a::FunctionDetails, b::FunctionDetails)` in `src/genome/codegen.jl` from `hash(a) == hash(b)` to direct field comparison (`a.name == b.name && a.args == b.args && a.return_type == b.return_type`), matching the `==` definition. Eliminates theoretical hash collision risk. `Base.hash` retained for Dict/Set usage.
