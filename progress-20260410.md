## Summary

The ablation experiment launched on 2026-04-09 completed overnight
(total wall 39551s ≈ 11 hr). All 4 variants × 5 seeds = 20 runs

top-3 programs with their fitnesses — is the clear winner.

## Key findings

1. **Elites alone > everything else.** The FunSearch pattern (showing
   scored programs) is the dominant signal. `elites_3` improved mean
   test by 0.011 and jumped from 1/5 to 4/5 seeds beating Best Fit.
   Best single result: seed 1337 at 1.0513 (5.2% better than BF).

2. **Adding fitness context and generation phase to elites hurts.**
   `full` (fitness + elites + generation) scored mean 1.0708 vs
   elites-only 1.0623. The extra prompt text likely distracts the
   model or pushes it toward conservative mutations. Simpler framing
   ("here are good programs, improve this one") outperforms richer
   framing ("here's your rank, phase, good programs, improve this").

3. **Fitness context alone is marginal.** `fitness_only` moved the
   mean by -0.0036 but inconsistently — helps on seeds 123 and 1337,
   neutral-to-slightly-worse on others. Knowing how bad you are
   without seeing what good looks like isn't actionable for the LLM.

4. **Wall time scales with prompt size.** baseline 1568s → elites_3
   2049s (+31%) → full 2374s (+51%). The extra tokens cost inference
   time; only elites_3 provides quality improvement that compensates.

5. **LLM parse success improves with enrichment.** baseline had 105
   deserialize-returned-nothing fallbacks out of ~6050 calls (1.7%),
   while enriched variants had 0–2. The enrichment preamble and
   "--- Program to mutate ---" separator give the LLM better framing
   for the expected input/output format. Zero sanitizer rejections
   across all variants.

6. **All variants: ~100% LLM pipeline success.** The `_build_sanitizer`
   fix from `d9932b9` is confirmed working. No sanitizer rejections
   in any of the 20 runs.

## Deserialize failure analysis

baseline had 105/6050 (1.7%) deserialize-returned-nothing fallbacks.
Enriched variants had 0–2. The enrichment preamble provides structural
framing ("--- Program to mutate ---") that helps the LLM distinguish
the code to modify from the surrounding context, producing more
reliably parseable output. This is a minor secondary benefit of the
enrichment mechanism beyond the primary information content.

## Next steps

- Commit ablation results and update overnight summary
- Consider follow-up: `ElitesSection(1)` vs `ElitesSection(5)` to
  find optimal k
- Consider whether the `full` variant's underperformance warrants
  simplifying the default recommended configuration to just
  `sections=[ElitesSection(3)]`
- **Need a benchmark where structure must evolve.** Bin packing is
  structurally "solved" from gen ~10 — every run converges to the
  same Best Fit while-loop skeleton, and the remaining optimization
  is constant/expression tuning inside the inner `if`. Early model
  scaling data suggests gemma4:e2b (5B) ties Haiku and Sonnet on this
  task because pattern-matching on short arithmetic is all that's
  needed. A harder benchmark should have: (a) no structural hint in
  the seed population, (b) multiple qualitatively different strategies
  at different fitness levels (e.g. single-pass vs nested vs
  recursive), and (c) a problem where the LLM's semantic
  understanding of the *domain* could guide structural decisions that
  random subtree mutation cannot. Candidates: scheduling with priority
  queues, multi-step planning with auxiliary state, symbolic regression
  on piecewise-discontinuous functions, or sorting without a seeded
  template (the ablation where type-1 sorting failed to discover
  nested loops, `progress-20260325.md:25`, is exactly this class of
  problem).
- **TODO: Log input/output token counts from LLM API responses.**
  The current `TrackedMutation` wrapper tracks wall time and call
  counts but not token usage. Both Anthropic and OpenAI-compatible
  APIs return `usage.input_tokens` / `usage.output_tokens` (or
  `prompt_tokens` / `completion_tokens`) in every response. The
  framework should extract and accumulate these so users can report
  total token budget per model, cost-per-improvement curves, and
  tokens-per-successful-mutation — metrics needed for a paper
  comparing LLM-assisted GP across model scales. Implementation:
  parse the `usage` field in `_extract_response_text` (or a new
  `_extract_usage` helper), accumulate on the `LLMMutationOperator`
  or expose via a callback, and surface in experiment result files.
  The model scaling experiment's Anthropic costs are currently only
  available via the Console UI; this would make them programmatic.
  Additionally, break down input tokens by component (system prompt,
  enrichment sections, genome source) using character-length
  estimation (~4 chars/token for code). All three strings are already
  computed separately in `_build_request_body` — accumulating their
  lengths requires only a few `+=` operations, no new instrumentation
  points. This enables reporting like "enrichment accounted for ~40%
  of input tokens" without requiring a tokenizer dependency. The
  API-reported exact totals serve as the ground truth for the
  aggregate; the per-component breakdown is the estimated split.

## Deserialize failure rate vs generation phase

Analysis prompted by LLM-evolution literature: do deserialize failures
concentrate early (simple programs) or late (complex evolved programs)?

| Model | Early (1-33) | Mid (34-66) | Late (67-100) |
|---|---|---|---|
| gemma4:e2b | 10.8/gen | 12.3/gen | 12.0/gen |
| Haiku 4.5 | 3.1/gen | 0.0/gen | 3.0/gen |
| Sonnet 4.6 | 4.6/gen | 3.1/gen | 3.0/gen |

**gemma4:e2b's failure rate is uniform across generations.** No
evidence that it fails more on evolved/complex programs. The failures
are an instruction-following limitation (code formatting: markdown
fences, explanations, etc.) not a code-complexity limitation. This
supports the "accidental diversity via classical fallback"
interpretation — the SubtreeMutation fallbacks are evenly distributed
across the run, providing consistent diversity injection rather than
concentrated in one phase.

## Confound: Best Fit template seeded in initial population

The custom solve in `examples/bin_packing.jl` seeds 10% of the
initial population (20 of 200 individuals) with the literal Best Fit
skeleton (type 4 in `_bp_seeded_body`, line 649). This is the exact
while/if/if structure that every evolved solution converges to.
Three other seed types (trivial, last-bin, First Fit) account for
another 30%, with the remaining 60% random.

**Consequence:** Type 4 dominates the population by generation ~3
(best fitness ~1.069 immediately). Evolution is reduced to
constant/expression tuning within a fixed structural template. The
LLM's elites_3 enrichment shows 3 near-identical Best Fit variants,
so the model just averages over copies of the same skeleton. This
explains why (a) no structural innovation ever appears, (b) model
scale doesn't correlate with fitness (tuning constants doesn't
require deep reasoning), and (c) gemma4:e2b ties Sonnet.

**Implication for the model scaling experiment:** The fitness numbers
measure "parameter tuning quality" not "structural discovery quality."
The deserialize failure rates and wall-time data are still valid and
useful. The fitness comparison is confounded.

**Future:** Re-run with types 1+2 only (trivial seeds, no loops) or
fully random initialization. This would be the first real test of
whether LLM-guided mutation can discover control flow structure, and
where model scale might genuinely matter. This directly connects to
the "need a benchmark where structure must evolve" item above.

## Near-term: behavioral initialization (MAP-Elites-style seeding)

The current random initialization (`_bp_random_initial_body`) produces
120 random programs per run, but they score ~1.7 (near worst-case)
and are purged by generation 3 when the seeded Best Fit template at
~1.069 dominates via tournament selection. Random programs provide
zero effective diversity.

**Proposed approach:** Generate a large pool of random programs
(e.g. 10,000), evaluate each, compute a behavioral fingerprint (the
same placement-decision vector used by `BehavioralSpeciation`), bin
by fingerprint, and sample N programs from each behavioral bin.
This guarantees the initial population contains structurally diverse
programs that exhibit *different behaviors*, not just different
syntax. Programs don't need to be good — they need to be different.

This is essentially a MAP-Elites initialization phase (Mouret &
Clune 2015). The framework already has the building blocks:
- Random code generation: `create_random_while_loop`,
  `create_random_if_statement`, `create_random_function_call`
  (`src/genome/codegen.jl`)
- Behavioral fingerprinting: user-provided `fingerprint_fn` in
  `BehavioralSpeciation` (`src/speciation.jl`)
- Evaluation: `evaluate` / `evaluate_genome`

The missing piece is the "generate many → evaluate → bin → sample"
loop, either as a general `BehavioralInitializer` type or as a
utility function that takes a fingerprint function and returns a
diverse initial population. Whether this ships in v0.1.0 or shortly
after is TBD, but improving random initialization quality is
important — the current approach wastes 60% of the initial
population on individuals that contribute nothing to search.
