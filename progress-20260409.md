# 2026-04-09 — Sanitizer whitelist bug: diagnosis and fix

## Summary

The post-fix LLM bin-packing rerun (launched 2026-04-08) completed
overnight. Both G1B (300 gen) and G2C (5 seeds × 100 gen) finished
without errors, but analysis of the logs revealed a second latent bug:
the ASTSanitizer was rejecting 98.9% of LLM mutations.

## Diagnosis

The `llm_ok` counter in the `TrackedMutation` wrapper
(`examples/bin_packing.jl:358`) is a wall-time heuristic (`dt > 0.5s`),
not an actual mutation success count. It measures "the HTTP call reached
the LLM" — not "the LLM output survived through the full pipeline."
The reported "100% LLM success" was misleading.

Actual counts from the G1B log (300 gens, seed 42):
- LLM HTTP calls: 3653
- Sanitizer rejections: 3612 (98.9%)
- Deserialize returned nothing: 41 (1.1%)
- Mutations that actually used LLM output: ~0

**Root cause:** `src/llm_operator.jl:197` constructed `ASTSanitizer()`
with `DEFAULT_SAFE_CALLS` — a whitelist of math operators, type
conversions, and Julia builtins. Domain-specific functions like
`bp_n_bins`, `bp_bin_remaining`, `bp_place_in_bin` are NOT in that
default set.

The deserializer's `_is_valid_call` (`src/genome/expr_genome.jl:316`)
correctly validates function calls against the GenState's function set
(which includes `bp_*`). But the sanitizer then re-checks against its
own, narrower whitelist and rejects the same calls.

**Why this was masked pre-parser-fix:** The old parser stripped all
control flow and kept only assignments. Assignments use operators
(`+`, `-`, `*`) which are in `DEFAULT_SAFE_CALLS`. The `bp_*` calls
lived inside `while`/`if` blocks that the parser was discarding before
the sanitizer ever saw them. The sanitizer has always had this
limitation — it was just never exercised by any LLM output that
survived parsing.

**Why the `llm_ok` metric didn't catch it:** `TrackedMutation` uses a
0.5-second threshold to distinguish "LLM inference happened" from
"instant fallback to SubtreeMutation." Since the sanitizer runs *after*
the HTTP call, a rejected-then-fallen-back mutation still takes >0.5s
(the LLM inference time) and gets counted as "ok." The metric is
structurally unable to detect sanitizer rejections.

## Fix

Added `_build_sanitizer(state::GenState)` in `src/llm_operator.jl`
that constructs an `ASTSanitizer` whose whitelist is
`union(DEFAULT_SAFE_CALLS, {fd.name for fd in state.funcs.funcs})`.
Changed the sanitizer call at line 197 from `ASTSanitizer()` to
`_build_sanitizer(g.state)`.

This way, any problem-specific primitives registered in the function
set are automatically included in the sanitizer's whitelist. The
deserializer and sanitizer now agree on what function calls are
permitted.

## Files modified

- `src/llm_operator.jl` — added `_build_sanitizer`, changed sanitizer
  construction at the call site

  the previous run). Fix confirmed working.

## Decisions

- **Not fixing `llm_ok` metric now.** The timing heuristic is
  fundamentally limited but changing the `TrackedMutation` interface
  mid-experiment would invalidate comparisons. Flagged for future work:
  the metric should count actual pipeline-survived mutations, not
  wall-time thresholds.
- **Not rerunning G1A.** The classical control does not go through the
  LLM operator or sanitizer. Run 2's G1A results (train 1.0693, test
  1.0637) are the valid matched baseline.
- **Kept run 2 results in archive.** They're the empirical proof of the
  sanitizer bug's impact (99% fallback rate → effectively classical
  performance). Useful evidence if we ever question whether the
  sanitizer is load-bearing.
