# 2026-04-12 — Unseeded model scaling: early observations

## Experiment status

Unseeded model scaling experiment launched 2026-04-11. gemma4:e2b and
gemma4:e4b completed; gemma4:26b running; qwen3-coder:30b pending.

## Early observation: no control flow in evolved programs

Best programs from the unseeded runs (200 gen, random init) are flat
sequences of `bp_place_in_bin(N)` with hardcoded bin indices. No while
loops, no if statements, no bin-scanning logic. Fitness ~1.78 (barely
above worst-case, far from the ~1.07 that seeded Best Fit achieves).

200 generations was not enough for GP to discover the while-loop
scanning pattern from scratch. The population appears stuck in a local
optimum of "memorize a few good bin indices" rather than discovering
the general "scan bins and pick the best fit" strategy.

## TODO: investigate population initialization diversity

The random initialization (`_bp_random_initial_body`) does generate
while loops and if statements (15% and 10% probability per statement
respectively, `bin_packing.jl:592-597`). Questions to answer:

1. **What does the initial population actually look like?** How many
   of the 200 random programs contain while loops? How many contain
   `bp_bin_remaining` calls (the key primitive for scoring bins)?
   The generation probabilities suggest ~15% of 4-7 statements = ~1
   while loop per program, but with random conditions and bodies
   these are almost certainly nonsensical.

2. **Do control-flow programs survive past generation 1?** If random
   while-loop programs score ~2.0 (same as random assignment-only
   programs), tournament selection has no reason to prefer them.
   Control flow would need to provide a fitness advantage to be
   selected, but random control flow is unlikely to be better than
   random hardcoded bin placements.

3. **Is the issue generation (programs aren't being created with
   useful structure) or selection (programs with structure are
   created but immediately outcompeted)?** Logging the structural
   composition of the population at gen 1 vs gen 50 vs gen 200 would
   answer this. If while-loop programs exist at gen 1 but vanish by
   gen 50, the issue is selection pressure. If they don't exist at
   gen 1, the issue is the generator.

4. **Would `behavioral_initialize` help here?** If the pool of
   10,000 random programs includes even a few that accidentally
   scan bins (producing different placement fingerprints), behavioral
   binning would guarantee they survive into the initial population.
   This is exactly the use case `behavioral_initialize` was built for.

5. **Is the LLM contributing anything in the unseeded setting?**
   With `elites_3` enrichment showing 3 programs that are all flat
   `bp_place_in_bin(N)` sequences, the LLM has no structural template
   to learn from. It's being asked to improve garbage by looking at
   more garbage. Model scale can't help here — the bottleneck is the
   quality of the elites, not the intelligence of the mutator.

This investigation should happen before running more unseeded
experiments — the current setup may be fundamentally unable to
discover structure, regardless of model scale or generation count.

## Critical finding: LLM mutations are 99-100% rejected in unseeded runs

| Model | LLM calls | LLM ok | Deser failures |
|---|---|---|---|
| gemma4:e2b | 2482 | **0** (0.0%) | 12171 (across 5 seeds) |
| gemma4:e4b | 2414 | **22** (0.9%) | 12084 (across 5 seeds) |

The LLM is responding but nothing survives deserialization. This is
a different failure mode from the seeded experiment (where 50% of
gemma4 output failed to parse). In the unseeded case, the elites
shown to the LLM are flat `bp_place_in_bin(N)` sequences. When the
LLM tries to introduce a while loop (which `BP_LLM_SYSTEM_PROMPT`
explicitly encourages), the structurally novel output may fail
type-checking during deserialization — the type-checker validates
assignments, conditions, and calls against the parent's GenState,
and a wholesale structural change (from flat calls to a while loop
with if-conditions) may produce expressions that don't pass.

**This means the unseeded experiment is running as pure classical GP
with zero LLM contribution.** The model scaling comparison is
measuring classical GP performance, not LLM-assisted GP. The prompt
enrichment (elites_3) is counterproductive here because it shows the
LLM garbage programs that provide no useful structural template.

## TODO: provide problem description to the LLM

Alan's observation: "giving the LLM a concrete description of the
overall problem being solved would be useful — why deprive the model
of relevant information?"

The `BP_LLM_SYSTEM_PROMPT` already contains a problem description
and even the hint "A while loop scanning from bin 1 to bp_n_bins()
with a conditional tracking the best bin found so far is the key
structure to discover." But the model isn't producing parseable
output despite this hint.

For a general framework feature, consider adding a `ProblemDescriptionSection`
to the prompt enrichment system that injects a user-provided natural
language description of the optimization target. This would complement
`ElitesSection` (which shows code examples) with semantic context
(which explains what the code should accomplish). The combination
would be especially important in the unseeded case where the elite
programs are uninformative.

## Root cause hypothesis

The 99-100% deserialization failure rate in the unseeded case likely
has a specific technical cause worth investigating:

1. **Type-checker rejects structurally novel programs.** The
   `_is_valid_statement` validator recursively checks all assignments,
   conditions, and calls against the GenState. If the LLM introduces
   a while loop where the parent had none, the condition expression
   must type-check to Bool and all body statements must type-check
   against the available variables. Random variable references and
   novel control flow may fail these checks.

2. **`repr()` format confuses the LLM.** The serialized elites use
   `repr()` output like `:(bp_place_in_bin(3))` with the `:()` quote
   wrapper. The LLM's response may mirror this format or produce a
   mix of quoted and unquoted Julia, confusing the parser.

3. **Enrichment text overwhelms the code.** With 3 flat programs in
   the elites section plus the genome to mutate, the user message
   is mostly repetitive `bp_place_in_bin(N)` sequences. The LLM may
   anchor on this pattern rather than the system prompt's structural
   hints.

Diagnosis: capture a sample of raw LLM responses from the unseeded
run (before deserialization) to see what the models are actually
producing. This would distinguish "LLM produces valid while loops
that fail type-checking" from "LLM produces garbled output."

## Debug logging results: qwen3-coder produces Best Fit from scratch

Added `debug_log` field to `LLMMutationOperator` — optional IO handle
that writes the serialized parent, raw LLM response, and pipeline
outcome for each call. Ran a diagnostic: 10 gen, 50 pop, random init,
qwen3-coder:30b with elites_3.

**Result: 29 calls, 29 successes (100%).** qwen3-coder:30b produces
valid Best Fit while-loop programs on *every single call*, regardless
of what garbage the parent is. Example from call 1 (parent is random
assignments + `if true` blocks):

```
INPUT:  :(__temp_2 = __temp_1 - __temp_3)
        :(if true ... end)
        :(bp_place_in_bin(43))
        ...

OUTPUT: :(__temp_1 = 1)
        :(__temp_2 = 2147483647)
        :(while __temp_1 <= bp_n_bins()
            __temp_4 = bp_bin_remaining(__temp_1)
            if __temp_4 >= bp_item_size() && __temp_4 < __temp_3
                __temp_2 = __temp_1
                ...
        :(if __temp_2 != 2147483647
            result = bp_place_in_bin(__temp_2)
        ...
OUTCOME: success
```

The model is essentially ignoring the parent and producing a clean
Best Fit implementation from the system prompt alone. Every call
outputs the same structural template with minor constant variations.

**This means the unseeded experiment's 0% success rate was entirely
due to gemma4's poor instruction following, not a framework or
deserializer problem.** qwen3-coder:30b (code-tuned, 2% deser
failure in seeded experiments) parses perfectly. gemma4 models
(~50% deser failure in seeded experiments) dropped to ~0% in the
unseeded case — likely because the garbled parent programs (which
include `repr()`-format `:()` quote wrappers) confused the models
further.

**Implication:** The unseeded model scaling experiment should be
re-run with qwen3-coder:30b only. gemma4 models cannot produce
parseable output reliably enough for the LLM to contribute. The
"model scaling" question on this benchmark reduces to "can the
model follow instructions?" — and the answer is binary (qwen3-coder
yes, gemma4 no) rather than a smooth scaling curve.

**Second implication:** The LLM is not actually "evolving" structure
here — it's pattern-matching from the system prompt to produce the
same Best Fit template every time, regardless of the parent. This is
FunSearch's "island of competence" problem: the LLM produces one
good program and selection spreads it, but the LLM doesn't explore
structural variations. For a harder benchmark, the system prompt
would need to describe the problem without hinting at the solution.
