# Progress Log — 2026-03-24

## Sorting Algorithm Evolution Example

### Summary

Implemented `examples/sorting.jl` — a new built-in example for Arborist.jl that demonstrates evolving a comparison-based sorting algorithm from scratch using genetic programming with curriculum learning. This follows the same side-effectful simulator pattern established by `AntGenome` and `bin_packing.jl`.

### Files Created

- `examples/sorting.jl` — complete sorting example (~580 lines), runnable as standalone script
- `examples/sorting_results.md` — auto-generated results from test runs

### Design Decisions

**Architecture: ExprGenome + custom solve (not a new genome type)**
- Followed the bin_packing.jl pattern rather than creating a new genome type like AntGenome
- Custom `solve` method dispatches on `GPProblem{ExprGenome, CurriculumSortingEvaluator}`
- Custom `evaluate_genome` methods for both `SortingEvaluator` and `CurriculumSortingEvaluator`
- Why: ExprGenome already provides all needed machinery (typed variables, control flow, loops). A custom genome type would duplicate infrastructure without adding value.

**No sort_set! primitive**
- Only `sort_get`, `sort_n`, `sort_less`, `sort_swap!` exposed to evolved programs
- Why: Forces swap-based sorting, preserves multiset property, dramatically reduces search space, and makes correctness verification trivial (just check if sorted)

**Curriculum learning**
- Starts at array length 3, advances when best fitness < 0.05 (upgrade_threshold)
- Re-evaluates entire population when curriculum advances to new length
- Loop limit scales as `10 * n²` with curriculum length
- Why: Without curriculum, evolution on length-8 arrays struggles to find gradient. Length-3 arrays are trivially solvable, providing immediate signal.

**Seeded initial population**
- 4 template types: single-pass bubble kernel, nested bubble sort, reverse-direction pass, selection sort skeleton
- ~40% of population seeded, rest random
- Why: Provides useful starting points with nested loop structure that evolution can refine. Random-only populations take longer to discover the nested-loop pattern.

**8 Int32 temp variables (no Float32)**
- Sorting only needs integer indices, so all temps are Int32
- Why: Float32 temps would pollute the search space with irrelevant arithmetic. The function set includes only Int32 arithmetic (+, -) and Int32 comparisons.

### Test Results

**Smoke test (pop=20, gen=5, seed=42):**
- Curriculum: 3 → 4 in 1 generation
- Best fitness: 0.0125 (bloat penalty only, 0 sorting errors)
- Verification: 100% correct on all lengths 3-12
- Evolved a clean selection sort
- Wall time: 1.6s

**Medium test (pop=50, gen=30, seed=123):**
- Curriculum: 3 → 4 → 5 → 6 in first 3 generations
- Best fitness: 0.0115
- Verification: 100% correct on all lengths 3-12
- Also evolved selection sort (from seeded template)
- Wall time: 16.8s

**Achievement: Tier 2 (target)** — 100% correct on length-8 with full generalization to length-12. The seeded selection sort template is already a correct algorithm; evolution preserves and slightly simplifies it.

**Existing test suite: All 1172 tests pass** (1171 pass + 1 pre-existing broken), no regressions.

### Key Implementation Details

- `SortState` mutable struct with module-level `Ref` (same pattern as AntGenome)
- All index operations clamp to [1, n] — evolved programs never crash on out-of-bounds
- Fitness = mean normalized inversion count across episodes (partial credit provides gradient)
- Pretty-printer strips LineNumberNode artifacts for clean output
- Verification uses separate RNG seed (999) from training (42) to test generalization
- Results auto-saved to `examples/sorting_results.md` with tier assessment

### Next Steps

- Consider running with larger populations and without seeded templates to see if evolution discovers sorting algorithms de novo (rather than just preserving seeded ones)
- Could add experiment modes similar to bin_packing.jl (multi-seed, extended runs)
- The non-seeded population members have not yet been observed to independently discover correct sorting — this would be the more interesting GP result

## Comparison Count Penalty Experiments

### Goal

Add a secondary fitness term to reward programs that sort with fewer comparisons, creating pressure toward algorithms with better time complexity than O(n²) selection sort.

### Design

- **Fitness formula:** `fitness = inversion_fitness + α × mean(comparisons / (n · log₂ n))`
- **Adaptive α:** `α = comparison_alpha_base × max(0, current_length − 6)` — zero for curriculum lengths ≤ 6 (correctness only), increases linearly so the penalty only becomes meaningful at lengths where the O(n²) vs O(n log n) gap is large
- **Curriculum extended:** target_length raised from 8 to 20, since the quadratic/linearithmic difference at n=12 is only ~2.5× but at n=24 is ~5×
- **Verification table:** expanded to show comparisons, swaps, comps/n², and comps/(n·lg n) per length, plus a complexity characterization

### Run 1: Ungated penalty (α additive on all episodes)

**Parameters:** pop=300, gen=500, seed=42, target_length=20, α_base=0.05

**Result: FAILURE — broke correctness.** The evolved program incremented the inner loop by 5 instead of 1, reducing comparisons from n(n-1)/2 to ~n/5 · n = n²/5, but only examining a fraction of the array. At α=0.3 (length 12), saving 51 comparisons (worth 0.3×51/43 ≈ 0.36 fitness) vastly exceeded the correctness cost (~0.05 inversions from missing pairs). The program scored 0.27 vs a perfect selection sort's 0.46.

**Root cause:** The comparison penalty reward for skipping work exceeded the inversion penalty for incorrect sorting. The fitness landscape had a steeper gradient toward fewer comparisons than toward correctness.

### Run 2: Gated penalty (comparison cost only counted on correctly-sorted episodes)

**Fix applied:** Only accumulate comparison penalty for episodes where `issorted(arr)` is true after execution.

**Bug 1: Curriculum stuck at length 8.** The curriculum advancement checked `fitnesses[1]` — the best individual by total fitness. But with the gated penalty, a correct sorter pays comparison cost on all 30 episodes while a mostly-incorrect sorter pays near-zero. An incorrect program with 5% inversions (fitness ~0.05 + 0 comparison) outranked a correct selection sort (fitness 0 + 0.1×1.17 ≈ 0.12). The curriculum never advanced because genomes[1] wasn't actually correct.

**Fix applied:** Check the top `4 × elitism` individuals for correctness, advancing if ANY of them sort correctly at the current length.

**Bug 2: Still selected incorrect programs.** After fixing curriculum advancement, the curriculum advanced to length 20 (α=0.7), but the best-by-fitness individual was still an almost-correct selection sort variant (`__temp_3 = __temp_1 - -1` — initializes minimum to i+1 instead of i) that scored ~0.03 total (small inversions + near-zero comparison cost on the few correctly-sorted episodes) vs a correct program scoring ~0.1+ (zero inversions but full comparison cost).

**Result:** 0.1-0.6% accuracy across all lengths. The gated penalty prevents *directly* trading correctness for fewer comparisons, but it creates a subtler problem: programs that are *mostly* correct get low total fitness because they pay comparison cost on few episodes, while perfectly correct programs pay full comparison cost and rank lower.

### Key Finding

**Additive comparison penalties (even gated on correctness) create perverse selection pressure when α is large relative to the inversion scale.** The fundamental issue is that the fitness function has two optima:
1. Sort correctly, pay high comparison cost → total ~0.12 at α=0.1
2. Sort incorrectly with small inversions, pay ~zero comparison cost → total ~0.05

Option 2 dominates whenever `α × comps/(n·lg n) > mean_inversions`, which happens easily for selection sort at moderate α.

### Alternatives Not Yet Tried

1. **Lexicographic fitness:** Sort by correctness first, comparison count second. Any correct program beats any incorrect one regardless of comparison count. This is the cleanest solution but requires modifying the fitness comparison throughout the solve loop.
2. **Very small α (~0.01):** Makes the comparison term a tiebreaker that never dominates the correctness signal. Simple but may not exert enough pressure to actually change the algorithm structure.
3. **Threshold gating:** Only apply comparison penalty when correctness is perfect (inversion_count = 0 for ALL episodes), treating it as a reward for already-correct programs. This avoids the partial-correctness exploit.
