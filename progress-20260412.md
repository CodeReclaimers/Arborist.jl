# 2026-04-12 — Unseeded model scaling: early observations

## Experiment status

Unseeded model scaling experiment launched 2026-04-11. gemma4:e2b and
gemma4:e4b completed; gemma4:26b running; qwen3-coder:30b pending.

## Early observation: no control flow in evolved programs

Best programs from the unseeded runs (200 gen, random init) are flat
sequences of `bp_place_in_bin(N)` with hardcoded bin indices. No while
loops, no if statements, no bin-scanning logic. Fitness ~1.78 (barely
above worst-case, far from the ~1.07 that seeded Best Fit achieves).

200 generations was not enough for GP to discover the while-loop
scanning pattern from scratch. The population appears stuck in a local
optimum of "memorize a few good bin indices" rather than discovering
the general "scan bins and pick the best fit" strategy.

## TODO: investigate population initialization diversity

The random initialization (`_bp_random_initial_body`) does generate
while loops and if statements (15% and 10% probability per statement
respectively, `bin_packing.jl:592-597`). Questions to answer:

1. **What does the initial population actually look like?** How many
   of the 200 random programs contain while loops? How many contain
   `bp_bin_remaining` calls (the key primitive for scoring bins)?
   The generation probabilities suggest ~15% of 4-7 statements = ~1
   while loop per program, but with random conditions and bodies
   these are almost certainly nonsensical.

2. **Do control-flow programs survive past generation 1?** If random
   while-loop programs score ~2.0 (same as random assignment-only
   programs), tournament selection has no reason to prefer them.
   Control flow would need to provide a fitness advantage to be
   selected, but random control flow is unlikely to be better than
   random hardcoded bin placements.

3. **Is the issue generation (programs aren't being created with
   useful structure) or selection (programs with structure are
   created but immediately outcompeted)?** Logging the structural
   composition of the population at gen 1 vs gen 50 vs gen 200 would
   answer this. If while-loop programs exist at gen 1 but vanish by
   gen 50, the issue is selection pressure. If they don't exist at
   gen 1, the issue is the generator.

4. **Would `behavioral_initialize` help here?** If the pool of
   10,000 random programs includes even a few that accidentally
   scan bins (producing different placement fingerprints), behavioral
   binning would guarantee they survive into the initial population.
   This is exactly the use case `behavioral_initialize` was built for.

5. **Is the LLM contributing anything in the unseeded setting?**
   With `elites_3` enrichment showing 3 programs that are all flat
   `bp_place_in_bin(N)` sequences, the LLM has no structural template
   to learn from. It's being asked to improve garbage by looking at
   more garbage. Model scale can't help here — the bottleneck is the
   quality of the elites, not the intelligence of the mutator.

This investigation should happen before running more unseeded
experiments — the current setup may be fundamentally unable to
discover structure, regardless of model scale or generation count.

## Critical finding: LLM mutations are 99-100% rejected in unseeded runs

| Model | LLM calls | LLM ok | Deser failures |
|---|---|---|---|
| gemma4:e2b | 2482 | **0** (0.0%) | 12171 (across 5 seeds) |
| gemma4:e4b | 2414 | **22** (0.9%) | 12084 (across 5 seeds) |

The LLM is responding but nothing survives deserialization. This is
a different failure mode from the seeded experiment (where 50% of
gemma4 output failed to parse). In the unseeded case, the elites
shown to the LLM are flat `bp_place_in_bin(N)` sequences. When the
LLM tries to introduce a while loop (which `BP_LLM_SYSTEM_PROMPT`
explicitly encourages), the structurally novel output may fail
type-checking during deserialization — the type-checker validates
assignments, conditions, and calls against the parent's GenState,
and a wholesale structural change (from flat calls to a while loop
with if-conditions) may produce expressions that don't pass.

**This means the unseeded experiment is running as pure classical GP
with zero LLM contribution.** The model scaling comparison is
measuring classical GP performance, not LLM-assisted GP. The prompt
enrichment (elites_3) is counterproductive here because it shows the
LLM garbage programs that provide no useful structural template.

The `BP_LLM_SYSTEM_PROMPT` already contains a problem description

## Root cause hypothesis

The 99-100% deserialization failure rate in the unseeded case likely
has a specific technical cause worth investigating:

1. **Type-checker rejects structurally novel programs.** The
   `_is_valid_statement` validator recursively checks all assignments,
   conditions, and calls against the GenState. If the LLM introduces
   a while loop where the parent had none, the condition expression
   must type-check to Bool and all body statements must type-check
   against the available variables. Random variable references and
   novel control flow may fail these checks.

2. **`repr()` format confuses the LLM.** The serialized elites use
   `repr()` output like `:(bp_place_in_bin(3))` with the `:()` quote
   wrapper. The LLM's response may mirror this format or produce a
   mix of quoted and unquoted Julia, confusing the parser.

3. **Enrichment text overwhelms the code.** With 3 flat programs in
   the elites section plus the genome to mutate, the user message
   is mostly repetitive `bp_place_in_bin(N)` sequences. The LLM may
   anchor on this pattern rather than the system prompt's structural
   hints.

Diagnosis: capture a sample of raw LLM responses from the unseeded
run (before deserialization) to see what the models are actually
producing. This would distinguish "LLM produces valid while loops
that fail type-checking" from "LLM produces garbled output."

## NSGA-II with trace-derived auxiliary objectives

### Approach
Replaced the failed tournament tiebreaker with NSGA-II multi-objective
optimization. `BPMultiObjectiveEvaluator` wraps `BinPackingEvaluator`
to produce 3 objectives: `[primary_fitness, -coverage, -success_rate]`.
NSGA-II's non-dominated sorting preserves programs that are good on
*any* axis without needing tolerance parameters.

### Results (200 gen, 200 pop, behavioral init, qwen3-coder:30b)

Best primary fitness: **1.2493** (down from 1.34 behavioral init
baseline). Coverage of best: 3.008. Success rate: 0.186.

High-coverage programs reached cov=4.014 with sr=0.91 at
fitness=1.85. The Pareto front preserved both low-fitness/low-coverage
programs and high-coverage/worse-fitness programs as intended.

LLM: 2508 successes / 8 sanitizer rejections (99.7%).

### What worked
- **Coverage objective drove improvement.** Best fitness improved
  from 1.34 → 1.25, with coverage going from 0.0 to 3.0. Programs
  are now calling `bp_bin_remaining` ~3× per bin on average.
- **NSGA-II preserved diversity.** The Pareto front maintained both
  strategy types (low-fitness flat placers and high-coverage scanners)
  rather than converging to one.
- **LLM produced valid code at 99.7%.** Unicode fix + type coercion +
  improved system prompt all working.

### What didn't work
- **No while loops in any Pareto-optimal program.** Despite the LLM
  producing 190+ while-loop programs (82% of mutations), none
  survived on the Pareto front. The flat programs with hardcoded
  `bp_bin_remaining` calls achieved coverage=3.0 without loops,
  making the while-loop programs Pareto-dominated.
- **Coverage metric is gameable.** Flat programs achieve high
  coverage by including `bp_bin_remaining(__temp_1)` as standalone
  expressions (result discarded). The metric counts *calls*, not
  *conditional use of results*. A program that reads bins and ignores
  the result scores the same as one that reads bins and selects the
  best.

### Root cause: coverage ≠ intelligence
The coverage metric measures "how much state did you read" but not
"did you use what you read to make a decision." An `if bp_bin_remaining(i) >= bp_item_size()` is fundamentally different from a
standalone `bp_bin_remaining(i)` expression, but both increment the
coverage counter.

### Possible next steps
- **Conditional coverage metric:** count `bp_bin_remaining` calls
  that appear *inside if-conditions*, not standalone. This would
  require AST analysis rather than runtime counting.
- **Behavioral diversity objective:** use the existing behavioral
  fingerprinting (placement decision vector) as an objective rather
  than coverage. Programs that make *different placement decisions*
  are non-dominated regardless of fitness.
- **Success-rate-only objective:** drop coverage, keep only fitness +
  success_rate. Programs that waste calls on failed placements are
  dominated by programs that place efficiently. This might indirectly
  favor structured programs without being gameable.
- **Accept the result:** 1.25 from unseeded random init is a
  legitimate GP result. The programs discovered a heuristic (place in
  bin bp_n_bins(), query some bins) without being told the answer. The
  fact that they didn't discover the while-loop pattern may simply
  reflect that 200 generations isn't enough for structural innovation
  on this problem, regardless of objectives.

## Debug logging results: qwen3-coder produces Best Fit from scratch

Added `debug_log` field to `LLMMutationOperator` — optional IO handle
that writes the serialized parent, raw LLM response, and pipeline
outcome for each call. Ran a diagnostic: 10 gen, 50 pop, random init,
qwen3-coder:30b with elites_3.

**Result: 29 calls, 29 successes (100%).** qwen3-coder:30b produces
valid Best Fit while-loop programs on *every single call*, regardless
of what garbage the parent is. Example from call 1 (parent is random
assignments + `if true` blocks):

```
INPUT:  :(__temp_2 = __temp_1 - __temp_3)
        :(if true ... end)
        :(bp_place_in_bin(43))
        ...

OUTPUT: :(__temp_1 = 1)
        :(__temp_2 = 2147483647)
        :(while __temp_1 <= bp_n_bins()
            __temp_4 = bp_bin_remaining(__temp_1)
            if __temp_4 >= bp_item_size() && __temp_4 < __temp_3
                __temp_2 = __temp_1
                ...
        :(if __temp_2 != 2147483647
            result = bp_place_in_bin(__temp_2)
        ...
OUTCOME: success
```

The model is essentially ignoring the parent and producing a clean
Best Fit implementation from the system prompt alone. Every call
outputs the same structural template with minor constant variations.

**This means the unseeded experiment's 0% success rate was entirely
due to gemma4's poor instruction following, not a framework or
deserializer problem.** qwen3-coder:30b (code-tuned, 2% deser
failure in seeded experiments) parses perfectly. gemma4 models
(~50% deser failure in seeded experiments) dropped to ~0% in the
unseeded case — likely because the garbled parent programs (which
include `repr()`-format `:()` quote wrappers) confused the models
further.

**Implication:** The unseeded model scaling experiment should be
re-run with qwen3-coder:30b only. gemma4 models cannot produce
parseable output reliably enough for the LLM to contribute. The
"model scaling" question on this benchmark reduces to "can the
model follow instructions?" — and the answer is binary (qwen3-coder
yes, gemma4 no) rather than a smooth scaling curve.

**Second implication:** The LLM is not actually "evolving" structure
here — it's pattern-matching from the system prompt to produce the
same Best Fit template every time, regardless of the parent. This is
FunSearch's "island of competence" problem: the LLM produces one
good program and selection spreads it, but the LLM doesn't explore
structural variations. For a harder benchmark, the system prompt
would need to describe the problem without hinting at the solution.

## Unicode escape fix reveals a deeper issue

After fixing `\uXXXX` unicode escapes in `_find_last_json_string`
(`7cd82c7`), re-ran the diagnostic: 49/52 LLM calls succeed (94%).
The while loops now parse correctly — `<=` and `&&` are properly
unescaped before reaching `Meta.parse`.

**But fitness is still 1.94 after 20 generations with 49 successful
LLM mutations.** The LLM-generated Best Fit programs are
*structurally correct* but *semantically wrong*:

1. **0-indexed bin references:** `__temp_2 = 0` then
   `bp_place_in_bin(__temp_2)` — bins are 1-indexed, so bin 0
   always fails.
2. **Type mismatches:** `__temp_3 = 0.0f0` assigns Float32 to an
   Int32 variable (causes `deserialize_nothing`).
3. **Wrong initial sentinel values:** `__temp_2 = 2147483647` — uses
   Int64 max instead of a Float32 sentinel for the "best remaining
   capacity" tracker.

The system prompt describes the primitives and their types but doesn't
specify 1-indexing, initial value conventions, or that `__temp_1`
should start at `Int32(1)` not `1`. The LLM generates the right
*algorithm* but wrong *details* — and the deserializer's type checker
rejects the worst mismatches, while the subtler bugs (0-indexed bins)
produce programs that evaluate but score terribly.

**Three bugs found in this debugging session:**
1. `\uXXXX` unicode escapes not handled (fixed in `7cd82c7`)
2. LLM consistently produces 0-indexed bin references (system prompt
   issue — needs to specify 1-indexing)
3. LLM produces Int64 literals for Int32 variables (type promotion
   issue — `1` vs `Int32(1)`, `0` vs `Int32(0)`)

The type literal issue (#3) may warrant relaxing the deserializer's
type checker to allow Int → Int32 promotion for literal values, since
this is a semantic no-op that every LLM will get "wrong."

## NSGA-II with trace-derived auxiliary objectives

Pivoted from tiebreakers to NSGA-II multi-objective optimization
with objectives derived from the evaluation trace.

### Run 1: Three objectives — fitness, coverage, success_rate (`7f048d3`)

`BPMultiObjectiveEvaluator` wraps `BinPackingEvaluator` to produce
`[fitness, -coverage, -success_rate]`. Custom
`_nsga2_init_population` uses `behavioral_initialize` (10k pool).

**Result (200 gen, 200 pop, qwen3-coder):** Best fitness 1.2493.
Coverage 3.0 for top programs. **No while loops on the Pareto
front.** The coverage objective was *gamed*: evolution inserted
standalone `bp_bin_remaining` calls (result discarded) and even
`for` loops iterating over nonsensical bin indices just to inflate
the coverage counter. The metric counted *calls*, not *conditional
use of results*.

LLM: 2508/2516 successes (99.7%).
Hypervolume: stuck at 0.0 (reference point issue with 3 objectives).

### Run 2: Two objectives — fitness, success_rate (`c3c0350`)

Dropped coverage, kept only fitness + success_rate.

**Result (200 gen, 200 pop, qwen3-coder):** Best fitness **1.1962**
(improved from 1.2493). **`if` statements appeared in top programs**
— first structural innovation from unseeded init. Hypervolume
climbed steadily from 0.33 → 0.60 (converging but still improving
at gen 200).

Top of Pareto front by fitness:
- #1: fitness=1.1962, sr=0.133, has_if=yes
- #4: fitness=1.2164, sr=0.212, has_if=yes

Top by success rate:
- #1: fitness=1.9912, sr=1.0 (places everything but wastes bins)

The Pareto front preserved both extremes — low-fitness/low-sr
programs and high-sr/high-fitness programs — and evolution improved
both axes independently.

Programs evolved "clever flat placement" — computing bin indices
relative to `bp_n_bins()` via nested arithmetic. The `if`
statements are mostly `if true` (degenerate) but represent the
first structural step beyond pure assignments.

The success-rate objective is not gameable: the only way to increase
it is to actually place items in bins that fit.

### Key insight: objectives derived from runtime traces work, but
must measure *outcomes* not *activity*

Coverage (call count) is gameable — programs can call primitives
without using the results. Success rate (outcome of calls) is not
gameable — programs must interact correctly with state to increase
it. This distinction is the generalization: trace-derived objectives
should measure what the program *achieved*, not how much it *tried*.

## Run 3: Three objectives — fitness, success_rate, failed_placements (`fed423b`)

Added `failed_placements` (place_calls - place_successes) as a third
NSGA-II objective. The key insight: failed placements can only be
reduced by (a) always opening new bins (worsens fitness) or (b)
checking bin contents before placing (requires control flow). NSGA-II
naturally selects for (b) since (a) is Pareto-dominated on fitness.

### Result: **Best Fit discovered from scratch**

**Best fitness: 1.0687** — matches the Best Fit heuristic baseline
exactly. Achieved from fully unseeded random initialization in 200
generations with no structural hints in the system prompt.

Top 10 Pareto-optimal programs by fitness:

| # | fitness | success_rate | failed_placements | while | if |
|---|---------|-------------|-------------------|-------|----|
| 1-10 | 1.0687 | 0.462 | 2153 | no | yes |

Fewest-failed-placements programs:

| # | fitness | success_rate | failed_placements | while | if |
|---|---------|-------------|-------------------|-------|----|
| 1-5 | 1.9674 | 1.0 | 0 | no | yes |

LLM: 2461 successes / 32 sanitizer rejections (98.7%).

### The evolved Best Fit program

From the debug log (gen ~200 parent programs):

```julia
__temp_4 = 1.0f0
for __temp_3 = Int32(1):bp_n_bins()
    __temp_5 = bp_bin_remaining(__temp_3)
    if __temp_5 >= bp_item_size() && __temp_5 < __temp_4
        __temp_2 = __temp_3
        __temp_4 = __temp_5
    end
end
result = bp_place_in_bin(__temp_2)
```

This is a clean Best Fit implementation: scan all bins, track the
one with least remaining capacity that still fits the item, place
there. Uses `for` loop (not `while` — GP found `for` more evolvable
on this problem), `if` with capacity check and best-so-far
comparison, and a single `bp_place_in_bin` at the end.

### Why this worked when the previous attempts didn't

The `failed_placements` objective created selection pressure for
programs that *check before placing* — the `if __temp_5 >= bp_item_size()`
condition. Without this objective:
- The 2-objective run (fitness + success_rate) reached 1.1962 with
  `if` statements but no iterative scanning
- The 3-objective run with coverage reached 1.2493 but coverage
  was gamed by inserting junk `bp_bin_remaining` calls

With `failed_placements`:
- Programs that call `bp_place_in_bin` without checking get penalized
  (high failed_placements count)
- The only way to reduce failures while maintaining placements is to
  add conditional checks — which requires `if` statements
- Once `if` statements exist, the iterative scanning pattern (`for`
  loop over bins) provides a multiplicative benefit: checking all
  bins reduces failures proportionally
- This created a smooth fitness gradient from "flat placement" →
  "conditional placement" → "iterative conditional placement" (Best Fit)
